### F-S12-001 | high | security and integrity
File: server/auth.ts:226-256

What the code does: The API authentication middleware allows anonymous access to public board GET and PUT paths.

Why it is wrong: The allowlist includes data-changing PUT routes.

How it fails: An anonymous client can send a valid board payload to `/api/board` or `/api/board/:key`. The board route then replaces the shared board state through an upsert at `server/routes/board.ts:104-126`. The client can delete or alter shared tickets without a Bearer token.

Confidence: high

### F-S12-002 | high | usage limit enforcement
File: server/citationChecker.ts:437-444

What the code does: The citation run checks the user budget once before it queues all prompt and platform tasks.

Why it is wrong: The run can perform many provider calls after that single check. The provider call path records spend at `server/citationChecker.ts:363-371`, but it does not check the remaining budget.

How it fails: A user near the daily limit starts a run with many prompt and platform pairs. The initial check passes. The run then completes calls that exceed the limit because later calls do not recheck the budget.

Confidence: high

### F-S12-003 | high | usage accounting
File: server/citationJudge.ts:91-113

What the code does: The citation judge sends a direct OpenAI request and returns the parsed result.

Why it is wrong: This request does not call the required budget assertion or spend recording functions. The normal citation path calls the judge at `server/citationChecker.ts:394-396`.

How it fails: Each normal citation check performs a main provider call and a judge call. The main call records spend. The judge call does not. User usage and cost records undercount the actual provider usage.

Confidence: high

### F-S12-004 | high | run status correctness
File: server/citationChecker.ts:1252-1274

What the code does: The final citation run status becomes `succeeded` whenever the run inserts at least one check row.

Why it is wrong: A failed provider check still creates a ranking row at `server/citationChecker.ts:1117-1135`. The final status does not inspect those failure rows.

How it fails: A provider outage creates failure rows for the requested pairs. `totalChecks` is greater than zero. The run reaches `succeeded` with zero citations and no error message, although every check failed.

Confidence: high

### F-S12-005 | high | resume correctness
File: server/citationChecker.ts:617-648

What the code does: Resume mode skips every existing prompt and platform pair.

Why it is wrong: The code does not distinguish a successful result from a row created after a failed fetch. Failed fetches still create rows at `server/citationChecker.ts:703-712` and `server/citationChecker.ts:1117-1135`.

How it fails: A temporary timeout stores a failure row for a pair. The next advance operation marks the pair as already complete and skips it. The run never retries that pair, so the temporary failure becomes permanent run data.

Confidence: high

### F-S12-006 | high | job reliability
File: server/contentGenerationWorker.ts:81-103

What the code does: The worker throws a timeout when the remaining slice deadline reaches zero.

Why it is wrong: `runArticleSlice` treats the timeout as a terminal error at `server/contentGenerationWorker.ts:334-392`. Only an explicit deadline result at `server/contentGenerationWorker.ts:433-435` returns the job to a running state.

How it fails: Database work or a provider call consumes the slice deadline. The timeout exception reaches the failure handler. The worker marks the job slice as failed instead of deferring it for the next lease.

Confidence: high

### F-S12-007 | high | cross-brand data integrity
File: server/data/contentRequestArticleRepository.ts:58-81,203-236

What the code does: The article patch type permits `brandId`, and both update methods write the patch without removing that field.

Why it is wrong: The generation worker identifies the active job by article and job identifiers. It does not verify that the article still belongs to the job brand during completion at `server/databaseStorage.ts:1623-1692`.

How it fails: A user owns two brands. A job generates content for an article under Brand A. The user changes the article `brandId` to Brand B while the job runs. The job can then write Brand A content into the article that now belongs to Brand B.

Confidence: high

### F-S12-008 | medium | self-citation counting
File: server/citationChecker.ts:535-546,833-842,1437-1465

How it fails: Slice one cites a tracked URL and increments its self-citation count. Slice two cites the same URL. The second invocation has an empty set and increments the same URL again.

Confidence: high

### F-S12-009 | medium | brand matching correctness
File: server/citationChecker.ts:555-599,1030-1036

What the code does: Auto-discovery stores learned name variations in `variationCache`, but the own-brand check reads the original `brand.nameVariations` field.

Why it is wrong: The own-brand check does not use variations learned earlier in the same run.

How it fails: A response teaches a new alias for the current brand. Auto-discovery later reports that alias as an untracked competitor. The stale own-brand check does not reject it, so the system can create a false competitor.

Confidence: high

### F-S12-010 | medium | model output validation
