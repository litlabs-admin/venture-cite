# V3 production data destruction sweep

Scope: current worktree, `origin/main`, server code, shared schema, source code, scripts, migrations, tests, workflows, deployment files, and package lifecycle hooks.

This audit did not start Docker, start a database, connect to a database, run a migration, run `db:push`, send email, charge a card, or publish content.

The inventory covers persistent database mutations and DDL. In-memory `Map.delete`, `Headers.delete`, test mocks, and HTTP route declarations do not delete production database rows. I checked them and record the result under Cleared.

## What changed

The branch adds a stalled-autopilot `UPDATE brands` sweep, migration `0122` changes `api_costs.est_cost_cents` from integer to `numeric(12,6)`, and four Drizzle foreign-key declarations. The storage and retention files moved from `server/databaseStorage.ts` and `server/routes/cron.ts` into domain files. Their SQL and arguments match `origin/main`.

### db:push reachability and exact known drops

`package.json:18` exposes `npm run db:push`. `drizzle.config.ts:3-15` reads any `DATABASE_URL` and provides no production check. The package script, config, Render build and start commands, Vercel build command, GitHub workflows, Husky hook, and npm lifecycle hooks contain no automatic call to `db:push`.

The CI workflow starts local Supabase and uses `TEST_DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:55322/postgres` for integration tests. It never runs `db:push`. Production migration uses `scripts/migrate.ts` and `server/lib/migrationRunner.ts`; the runner reads sorted SQL files and does not read `shared/schema.ts`.

The current Drizzle schema contains 71 table objects. The migration history and runtime code prove these public tables exist or can exist but are absent from the Drizzle schema:

- `rate_limit_buckets`, created by `migrations/0043_rate_limit_buckets.sql:9` and used by `server/lib/rateLimitBuckets.ts:89-101`.
- `stripe_webhook_events`, created by `migrations/0002_webhook_idempotency.sql:8` and `migrations/0087_stripe_webhook_events.sql:30`, then used by `server/lib/stripeWebhookClaim.ts:20-45`.
- `schema_migrations`, created and used by `server/lib/migrationRunner.ts:174-189` and `217-274`.

If an operator runs `db:push` against a fully migrated production database, these three known tables are outside the Drizzle schema and are candidates for `DROP TABLE`. The same diff can drop any extra columns, indexes, constraints, or tables that exist outside the Drizzle schema. The exact out-of-band object set cannot be enumerated without connecting to the database, which this audit forbids.

The historical tables named by migrations `0068`, `0069`, `0070`, and `0086` are intentionally dropped by the migration history. They are not additional known live tables after the controlled migration sequence completes.

### Test and fixture database guards

`tests/helpers/destructiveDatabaseTest.ts:56-84` has these protections:

- Missing `TEST_DATABASE_URL` deletes `DATABASE_URL` from the test process and returns `skip`.
- A test URL cannot equal `DATABASE_URL` by normalized host, port, and database name.
- A non-local URL must contain a database name with a test boundary and cannot contain `prod` or `production` in its host.
- A remote test URL requires `ALLOW_REMOTE_TEST_DATABASE=1`.
- The local Supabase exception requires `LOCAL_SUPABASE_TEST=1`, host `localhost` or `127.0.0.1`, port `55322`, and database `postgres`.

The unit test `tests/unit/destructiveDatabaseTest.test.ts` covers these branches. I ran it with the autopilot test. The result was 21 passing tests.

The E2E helper is weaker. `tests/e2e/support/local-fixtures.ts:51-75` checks only that the app, Supabase, and database URLs use loopback hosts. A direct runtime call accepted `postgres://u:p@localhost:5432/production`. `playwright.config.ts:78-106` applies a fixed local Supabase guard only when it starts the local web server. A run with `E2E_BASE_URL` set does not use that web-server guard, so the fixture's weaker check can reach a real loopback database.

### Seed and reset scripts

No script under `scripts/` runs `DELETE`, `TRUNCATE`, `DROP TABLE`, or `DROP SCHEMA` against a database as a reset or reseed operation. `scripts/assertMigrationsApplied.mjs` and `scripts/checkSchemaDrift.ts` read database state. `scripts/syncSupabaseMigrations.mjs` and `scripts/verifySchemaSplit.mjs` generate or inspect files. `scripts/seed-stripe-products.ts` and `scripts/setup-stripe-products.ts` create external Stripe products. They do not delete database rows, but they have no production-mode guard and can create Stripe objects if an operator supplies a live Stripe key.

## Findings

### V3-001 | high | `package.json:18`, `drizzle.config.ts:3-15`

What it deletes: A confirmed `db:push` can drop `rate_limit_buckets`, `stripe_webhook_events`, `schema_migrations`, and any other production table or column absent from the Drizzle schema. It can also apply destructive indexes, constraints, or type changes.

Why it is a risk: The command accepts any `DATABASE_URL` and has no production refusal. Drizzle Kit itself warns that data-loss statements can truncate tables and data. This command already existed on `origin/main`, so this is not branch-introduced.

Concrete sequence that destroys production data: set `DATABASE_URL` to the production URL, run `npm run db:push`, approve the generated destructive statements or pass `--force`, and allow Drizzle Kit to apply the diff.

Confidence: high for reachability and the three known omitted tables. Low for additional out-of-band objects because no database connection was allowed.

### V3-002 | high | `tests/e2e/support/local-fixtures.ts:51-75,120-140`

What it deletes: The fixture deletes one `public.users` row by generated user id and sends a Supabase Auth admin delete for the same id. Existing foreign-key cascades delete that user's child rows.

Why it is a risk: The helper accepts a loopback URL with a production database name. It does not require the fixed local Supabase port, the `postgres` database, or a test database name. The generated id limits the intended target, but the code does not prove that the target database is disposable.

Concrete sequence that destroys production data: set all required `E2E_LOCAL_*` variables, set `E2E_LOCAL_DATABASE_URL=postgres://...@localhost:5432/production`, set `E2E_BASE_URL` so the Playwright web-server guard is bypassed, run a local E2E spec, and let account cleanup execute.

Confidence: high. I ran the real helper with that URL and it accepted the configuration.

### V3-003 | medium | `server/lib/onboardingAutopilot.ts:425-432`

What it deletes: No rows. It overwrites `autopilot_status` with `failed` and overwrites `autopilot_error` for every matching stale brand.

Why it is a risk: The new statement has no tenant or brand argument. One resume sweep can change rows belonging to every tenant. The status filter and six-hour age filter limit the set, but the cross-tenant scope is intentional in the SQL and has no per-tenant authorization check.

Concrete sequence that destroys production data: run the daily cron or local boot resume sweep while two or more tenants have non-deleted brands in one of the four in-flight states for more than six hours. The statement changes all matching rows before the scan starts.

Confidence: high. `tests/unit/onboardingAutopilotResumeLoop.test.ts:179-221` proves the new update runs first and returns matched brand ids. The test does not prove tenant isolation because the SQL has none.

### V3-004 | medium | `migrations/0122_api_costs_cost_precision.sql:51-53`

What it deletes: No rows. It rewrites `api_costs.est_cost_cents` for every row when the old type is integer.

Why it is a risk: `numeric(12,6)` supports at most six integer digits before the decimal point. An existing integer greater than `999999` can fail the cast with numeric overflow. The migration runs inside the migration runner transaction, so a failure should roll back the migration, but it can block the release. Values within range preserve their numeric value, with only displayed scale changing.

Concrete sequence that destroys production data: no confirmed destructive sequence exists from this cast. A production row above the supported numeric range makes the release migration fail. The exact current production values were not checked because this audit forbids database access.

Confidence: high for the type-bound risk; low for whether production currently contains an out-of-range value.

### V3-005 | medium | `scripts/backfillMentionedBrands.ts:187-189`

What it deletes: No rows. It overwrites `geo_rankings.mentioned_brands` for every latest eligible row loaded by the script.

Why it is a risk: The script has no production guard and no tenant predicate. It defaults to applying writes unless `--dry-run` is supplied. This operation already existed on `origin/main`, so it is not branch-introduced.

Concrete sequence that destroys production data: run the script with a live production `DATABASE_URL` without `--dry-run`. It loads latest rows across all brands, calls the analyzer, and updates each row by id.

Confidence: high for the overwrite path. The script's source guard limits the written column, but no independent production safety guard exists.

## Verdict

DATA AT RISK UNDER STATED CONDITIONS

No automatic production data loss was found, and the retention moves plus foreign-key declarations match the origin behavior. Production data remains at risk if an operator runs the unguarded manual `db:push`, runs E2E cleanup against a loopback production database, or applies the new broad autopilot overwrite and the resulting cross-tenant state change is unacceptable.
