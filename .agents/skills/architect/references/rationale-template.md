# Rationale template

The prose that ships alongside the type sketch. One page. Sentence-case headings, no boilerplate. Replace the italic notes with actual content.

## Problem

_State the required behavior and the constraints that make the design non-obvious. Cite the existing types, callers, and invariants that the design must preserve._

## Usage (caller's view)

_Write this first. Show realistic caller code, imports, calls, and returned values. Derive the type sketch from this usage._

## Shape

_State the data types, module boundaries, validation points, and hidden complexity. Keep storage, transport, and framework types private._

## Decision

_State the chosen design and the evidence for it. If Codex agents supplied designs, state which parts you used._

## Tradeoffs accepted

_State material tradeoffs that a future reader might mistake for an oversight._

## Alternatives considered

_List meaningful alternatives. State why each lost. Do not list variants of the same design._

## Open questions and risks

_State unresolved risks as questions. Do not assume permission for a live-system action._

## Next implementation step

_The first thing to build against the sketch. One sentence. What you'd start writing immediately after synthesis (or after Phase D sign-off, if a checkpoint was opted into)._
